## Key design notes

- Auth is real (Supabase) but gated: `supabase.js` only creates a client when both env vars are set; otherwise sign-in is unavailable and the app still runs.
- `api.js` and `contentStore.js` are local-only (localStorage), so no backend is required for core features.
- Admin edits persist in `localStorage` (demo storage), not a server.
- New services live in `src/services/`; UI components call services/hooks, never Supabase directly.
- All layouts are separated: `MainLayout` (public), `AuthLayout` (auth), `AdminLayout` (admin). Never duplicate Header/Footer/Sidebar/Navbar.

## Authentication flow

1. App mounts and `AuthContext` initializes the Supabase client via `data/supabase.js`.
2. `session.js` `getInitialSession()` reads the existing Supabase session; `subscribeToSession()` listens for auth state changes.
3. Unauthenticated users navigating to protected routes are redirected to `Login` by `ProtectedRoute`.
4. `Login`/`Register` call Supabase sign-in/sign-up; on success the session is stored and `AuthContext` emits the authenticated user.
5. `RBACContext` loads the user's role and permissions from `db.js` once authenticated.
6. `Logout` clears the Supabase session and resets `AuthContext`/`RBACContext` state.
7. Profile updates (`Profile`, `EditProfile`) write through session/service helpers.

## Database schema

Supabase tables used by `data/db.js` and `data/session.js`:

- `profiles` (id UUID PK references auth.users, full_name TEXT, email TEXT, role TEXT DEFAULT 'student', avatar_url TEXT, created_at TIMESTAMPTZ, updated_at TIMESTAMPTZ)
- `roles` (id UUID PK, name TEXT UNIQUE, description TEXT)
- `permissions` (id UUID PK, name TEXT UNIQUE, description TEXT)
- `role_permissions` (role_id UUID FK roles, permission_id UUID FK permissions, composite PK)
- `user_roles` (user_id UUID FK auth.users, role_id UUID FK roles, composite PK)

Row Level Security (RLS): profiles readable by all authenticated users; writable only by the owner or admins. Roles/permissions readable by all; writable only by admins.

## Role permissions

- `student`: read own profile, read notes/syllabus/notices, update own profile/avatar
- `teacher`: all student permissions plus manage notes and syllabus entries
- `admin`: all permissions including user management, role assignment, permission grants, full content moderation

Permission checks are performed via `RBACContext` (`hasPermission(permissionName)`, `hasRole(roleName)`) and enforced by `ProtectedRoute` at route level.

## Supabase integration

- `data/supabase.js` exports a singleton `supabase` client created from `REACT_APP_SUPABASE_URL` and `REACT_APP_SUPABASE_ANON_KEY`; returns null if env vars are missing.
- New services in `src/services/supabase/` wrap all Supabase operations.
- `data/session.js` wraps sign-in, sign-up, sign-out, session retrieval, auth-state subscription, and profile updates.
- `data/db.js` exposes typed helpers: `getProfile`, `updateProfile`, `listUsers`, `getUserRoles`, `assignRole`, `listRoles`, `listPermissions`, `grantPermission`, `revokePermission`.
- All Supabase calls are wrapped in try/catch with `console.error` plus a user-facing message.
- Env vars must be `REACT_APP_*` prefixed; never log secrets. Add placeholders to `.env.example`.

## ProtectedRoute component

`src/components/ProtectedRoute/ProtectedRoute.js` — default export.

Wraps route elements and enforces:
1. Authentication: if no session, redirect to `Login` (with optional `from` return path).
2. Authorization: if `requiredRole` or `requiredPermission` props are set, check `RBACContext`; on failure redirect to `/unauthorized`.

Usage:
```jsx
<ProtectedRoute requiredRole="department_admin">
  <StudentManagement />
</ProtectedRoute>
```

Props: `children` (required), `requiredRole` (optional string), `requiredPermission` (optional string), `fallback` (optional, default `/login`).

## Bun-specific instructions

Runtime lock: `.bun-version` = `1.4.3`. `bunfig.toml` pins install/run/test behavior.
Package manager: **Bun only** — do not introduce npm/yarn/pnpm scripts or lockfiles (`package-lock.json` is legacy; `bun.lock` is authoritative).
Lockfile: `bun.lock` is committed; regenerate only via `bun install` after `package.json` changes.

Available scripts (all verified working):
- `bun install` — install from `bun.lock`
- `bun run dev` — Vite dev server (HMR), port 3000
- `bun run build` — Vite production build → `build/`
- `bun run start` — `vite preview` on port 3000
- `bun run preview` — alias for `start`
- `bun run test` — Bun test runner (Jest-compatible, jsdom shim)
- `bun run lint` — ESLint 9 flat config over `src/`
- `bun run typecheck` — `tsc --noEmit -p tsconfig.json`
- `bun run format` — Prettier over `src/**`

Dependency rule: prefer Bun-native tooling where it adds real value (test runner, lockfile, install speed). Do NOT replace working runtime dependencies (react, react-router-dom, supabase-js, framer-motion, three, @google/generative-ai) without justification.

## Coding conventions

- Files use `.js`/`.jsx` extensions; JSX via `react-jsx` (tsconfig `allowJs: true`, `checkJs: false`).
- React 19 with automatic runtime — `import React` is **not required** in JSX files. Prefer omitting it in new files.
- Named exports for utilities/context; default exports for page/layout components.
- SCSS per page/component, imported relatively.
- Env vars must be `REACT_APP_*` prefixed (Create React App requirement) or `VITE_*` (Vite). Never log secrets.
- Error handling: console.error + user-facing message; Supabase calls wrapped in try/catch.
- Lint: 0 errors is required. Warnings are tolerated (legacy codebase) but new code should be warning-free.

## Testing requirements

- Runner: Bun test (`bun test`), Jest-compatible.
- DOM: `src/testSetupDom.js` sets up `window.document`, `localStorage`, `matchMedia`, `IntersectionObserver`, and a stubbed `HTMLCanvasElement.getContext`.
- Matchers: `@testing-library/jest-dom` imported in each test file that needs DOM assertions.
- Place tests next to source as `*.test.js`/`*.test.jsx`.
- Wrap state updates in `act(...)` when testing interactive components.

## For future agents

1. Always run `bun install` after touching `package.json`; commit the updated `bun.lock`.
2. Do not commit `.env.local`, `Supabase Pass.txt`, `node_modules/`, `build/`, `bun.lockb`, or `graphify-out/`.
3. Keep `bun run lint`, `bun run typecheck`, `bun run test`, and `bun run build` green before considering a change complete.
4. New env vars must be added to `.env.example` (placeholder only) and prefixed `REACT_APP_` or `VITE_`.
5. Prefer minimal changes; do not rewrite working features or replace dependencies without justification.
6. When adding a new page/component, place it in the correct `src/features/<feature>/` folder and add the route in `src/app/routes/AppRoutes.js`.
7. Never import Supabase directly from a UI component — use services in `src/services/` and hooks in `src/hooks/`.
